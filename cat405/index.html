The project in 30 seconds

MyMakanRoute is a food hopping and food discovery planner, starting with Penang. It helps tourists and locals find hidden gems: food places that are well rated but not yet well known. The user picks a few places and the app plans the shortest walking route between them. Dijkstra’s algorithm on a real OpenStreetMap road network gives the walking times, and Ant Colony Optimisation chooses the visiting order. It is a CAT405 final year project in the Intelligent Computing major; the nature-inspired ACO is the “intelligent computing” part.

Migrations: building the database the same way everywhere

  • 001: places, PostGIS, a nearby_places() function (not used by the API)
  • 002: profiles and preferences
  • 003: itineraries and stops, with a deferrable unique (trip, position)
  • 004: revoke Supabase public rights, switch on RLS

migrate.js runs the numbered SQL files in order, each in a transaction, and records them in schema_migrations, so running it twice applies nothing new. seed.js checks the data with zod and upserts by osm_id; the OSM import never overwrites SAMPLE rows. There is deliberately no foreign key to Supabase’s own auth table, so the same migrations also run on a plain PostgreSQL test database.

Database security

Row Level Security is on for every table: places has one read-only rule, the others have none, so the public sees nothing in them. Supabase publishes tables through a public REST API automatically, so migration 004 revokes write rights from its anon and authenticated roles. Our backend connects as the table owner, so these rules do not limit it. The powerful service_role key is never used in the app.

1Why does the project need 55 SAMPLE places?

OSM has no ratings (0%), and the hidden gem rule needs a rating and a review count. The SAMPLE rows give the rule something to run on so the whole pipeline can be tested. Real Google ratings for those 55 are planned (step 2.9a).

2Why is the road network a file and not in Supabase?

The route planner reads the whole network on every request. Memory is much faster than querying the database each time, and it loads only once (about 0.2 s).

3Why is there no foreign key to the Supabase auth table?

So the same migrations also run on a plain PostgreSQL test database. The profile id simply equals the Supabase Auth user id.

4How is the database kept safe?

RLS on every table, public write rights revoked (migration 004), parameterised SQL, no service_role key in the app, secrets only in a .env file that is never committed.

5Why only 2.3% halal?

OSM volunteers rarely tag halal. The app should show “halal unknown” honestly; better sources (Google data, manual checks, user reports) are planned.

The idea

A hidden gem is “well liked, but not many people know it yet”, so it needs a high rating and few reviews.

LabelRule (defaults; set in config)
Hidden Gemrating ≥ 4.3 and 1 to 100 reviews
Popularmore than 100 reviews, whatever the rating
No labelno rating, 0 reviews, or few reviews with a lower rating

In code this is labelHiddenGem(), a pure function (same input, same output, no database), so it is easy to unit test. The thresholds come from settings (HIDDEN_GEM_MIN_RATING, HIDDEN_GEM_MAX_REVIEWS, POPULAR_MIN_REVIEWS). Why 4.3 and 100? They are starting values: 4.3 is clearly above average on most review sites and 100 reviews separates “known locally” from “famous”. Real Google data will show where they should sit.

Ranking

  1. Hidden Gems first, then Popular, then unlabelled.
  2. Inside each group, nearest first.
  3. A higher rating breaks ties.

Searching

GET /api/discovery/places takes lat, lng, radius (100 to 5,000 m, default 1,500), halal, maxPrice (1 to 4), cuisine, dietary, openNow, label and limit (1 to 100, default 50). PostGIS ST_DWithin finds places inside the radius, using a GiST index. Halal keeps only places marked halal; maxPrice means price level at most n; cuisine matches any of the given words (with % and _ escaped); dietary needs all the given tags. openNow and label are applied in JavaScript afterwards. The reply carries a note when sample data is present.

“Open now”

  • Hours are stored as JSON per day, e.g. morning and evening ranges
  • Checked in Malaysian time
  • Ranges past midnight work (18:00 to 02:00)
  • A closing time of 23:59 counts as 24:00
  • No structured hours = counted as not open

Four steps, in order: graph, snap, Dijkstra, ACO

POST /api/hopping/route takes 2 to 10 unique place ids, a travel mode (walking or driving, default walking), an optional start place and an optional seed. It returns the visiting order, the legs (time, distance and the road path to draw), the totals, a comparison of three methods and the algorithm settings.

1. The road graph

A graph is nodes joined by edges. Here a node is a junction or road end and an edge is a piece of road with a length and a travel time. It is built from OSM by build-road-graph.js (26,689 nodes, 34,732 edges); 99% of usable walking nodes sit in one connected part (26,208 of 26,478), and 97.7% for driving (22,918 of 23,448). Walking is 1.4 m/s and allowed both ways on one-way streets. Driving speed depends on road type (for example residential 20 km/h, primary 40, motorway 70) and respects one-way streets. These speeds are assumptions, not measurements.

2. Snapping

A place is not exactly on a road node, so it is snapped to the nearest node in the main connected part (so it never lands on an isolated piece such as a car park). A grid of about 220 m squares keeps the search fast; a place more than 1 km from any road cannot be routed (error 422 PLACE_NOT_ON_ROAD_GRAPH). If the road file is missing, a fallback links each place to its 4 nearest places with straight-line distance × 1.3.

3. Dijkstra’s algorithm

Finds the quickest path from one node to all others when no edge is negative. Keep a frontier ordered by best known time; always settle the closest unsettled node; relax its edges (“is going through here quicker?”). Because times are never negative, a settled node’s time is final. The code uses a binary min-heap (priority queue), cost O((V + E) log V), and stops early once all wanted stops are settled. It runs once per stop to build the time matrix: the walking time between every pair (10 × 10 for 10 stops, about 46 ms). If any pair is unreachable the API answers 422 ROUTE_UNREACHABLE.

4. The visiting order: a small TSP

Given the time matrix, which order has the smallest total time? That is the Travelling Salesman Problem, NP-hard. Routes here are open (start at the first or chosen stop, visit each once, do not return). With a fixed start there are (n − 1)! orders:

Ant Colony Optimisation, round by round

Real ants find short paths by leaving pheromone; shorter paths get walked more and collect more. Simple agents together find a good answer: swarm intelligence.

  1. Build orders. Each ant builds a full order from the start. At each step it picks the next unvisited stop at random with weight pheromoneα × (1/time)β (roulette-wheel selection). α = 1 weighs experience; β = 2 weighs closeness.
  2. Evaporate. Every trail times (1 − ρ), ρ = 0.5, so old information fades.
  3. Deposit. Each ant adds q / L on every move of its order (L = its total time, q = 1), so shorter orders add more. Elitist: the best order so far gets an extra deposit.
  4. Trail limits (MAX-MIN). Pheromone stays between τmin and τmax (τmin = 0.2 × τmax), where τmax = (ants + 1) q / (ρ × best time). No move becomes impossible, which avoids stagnation (all ants copying the first good order).

“Improved” vs “textbook” ACO

Textbook = the original Ant System (Dorigo, Maniezzo and Colorni, 1996) with β = 3, no elitist deposit, no trail limits. Improved adds the elitist deposit (from the Elitist Ant System), MAX-MIN trail limits (from the MAX-MIN Ant System, Stützle and Hoos) and β = 2. Both are kept in the code so the comparison can be reproduced.

1What is Dijkstra used for here, and why not straight-line distance?

To get the walking time between every pair of chosen places along real roads (the time matrix). Roads are not straight, so road times give realistic routes. Straight line × 1.3 is only the fallback when the road file is missing.

2Explain one round of ACO.

Ants build orders using pheromone and closeness; every trail evaporates by (1 − ρ); each ant deposits q/L on its moves and the best-so-far order gets an extra deposit; then pheromone is clamped between τmin and τmax. Repeat up to 200 times, or stop after 100 rounds without improvement.

3What do α, β and ρ do?

α = how much pheromone (experience) counts. β = how much closeness counts. ρ = how fast pheromone evaporates, so old choices fade.

4Why open routes?

Food hopping usually ends at the last stop; people do not need to walk back. A round trip could be added as an option.

5Why use a fixed seed?

The same input then gives the same route, which makes tests and the demo repeatable. Several seeds are planned for the larger evaluation.

6Give the time complexity of each method.

Dijkstra with a heap: O((V + E) log V) per stop. ACO: about O(iterations × ants × n²). Brute force: O((n − 1)!).

7Work out how many orders 6 stops have if the start is fixed. (my own sum)

(6 − 1)! = 5! = 5 × 4 × 3 × 2 × 1 = 120.

The question

The supervisor asked whether the proposed work is feasible. The answer in the report: yes. All four modules run end to end, and two gaps remain: real ratings and real user accounts. The report’s numbers can be regenerated with npm run feasibility (seeded, so the same each run).

Method

  • Walking mode
  • 4, 6, 8 and 10 stops
  • 10 random trips per size
  • Pool of 42 sample places (George Town, Pulau Tikus, Jelutong, Gurney)
  • Trips seeded 2026 + n; ACO seed 42
  • Brute force = the optimum (raised to 10 stops for this study)

Optimality gap = (method − optimum) / optimum × 100. Opt% = share of trips where the method found the optimum. One run on 5 Nov 2026 took 2.1 s.

Be honest about it

  • The results are indicative: 10 trips per size and one ACO seed. A larger test (50+ trips, several seeds, 12 to 20 stops, maybe a nearest-neighbour + 2-opt baseline) is planned.
  • At 10 stops brute force is faster than ACO (2.9 ms vs 7.26 ms). ACO is justified by scalability: orders grow factorially (479 million at 13 stops, 87 billion at 15) while ACO grows polynomially.
  • ACO is a heuristic. It is not always optimal.
  • Ratings behind the gem and analytics results are invented sample data.

Boss fight

Tap a question to reveal the model answer. Try it in your head first.

1Why use ACO if brute force is faster?

For 10 stops or fewer brute force with pruning is exact and fast (2.9 ms vs 7.26 ms), which is why it is the ground truth. But orders grow factorially (479 million at 13 stops, 87 billion at 15), and pruning does not stop that. ACO grows polynomially, so it scales to longer and multi-day trips. It is also the Intelligent Computing part. Next step: test 12 to 20 stops.

2How do you know the optimum?

Brute force tries every order, so it is exact. It was used as ground truth up to 10 stops.

3Is ACO always optimal?

No, it is a heuristic. In the test it found the optimum in 39 of 40 trips; the one miss was 2.03% longer.

4What is wrong with the evidence so far?

Only 10 trips per size, one ACO seed, up to 10 stops, and ratings are invented. The larger evaluation in Phase 3 is meant to fix the first three.

5Why is improved ACO better than textbook ACO here?

At 8 stops improved was 100% optimal against 60%; at 10 stops 90% against 70%, with a worst gap of 2.03% against 4.48%. The elitist deposit and MAX-MIN limits help it converge without stagnating. (Small test: indicative only.)

6Calculate the optimality gap if a route takes 19.3 min and the optimum is 17.9 min. (my own sum)

(19.3 − 17.9) / 17.9 × 100 = 1.4 / 17.9 × 100 ≈ 7.8%, which the report rounds to about 8%.

Three layers

The apps never talk to the database. Only the backend does. That keeps database passwords off the user’s device, keeps all rules in one place, and lets web and mobile share one API.

What happens when a user plans a trip

  1. The web app calls the search endpoint with a location and radius.
  2. The backend runs the PostGIS query, applies the hidden gem rule and ranks the places.
  3. The web app shows the list and a Leaflet map with labels.
  4. The user adds 2 to 10 places and presses Plan route.
  5. The backend loads the places, snaps them, runs Dijkstra for the time matrix, runs ACO (plus nearest neighbour and brute force for comparison), and builds the legs.
  6. The web app draws the route and shows minutes, metres and the comparison card.

API rules

  • REST: URLs are resources, the method says what to do
  • JSON everywhere
  • Success: {success:true, data}
  • Failure: {success:false, error:{code, message, details}}
  • Bad input: 400 VALIDATION_ERROR
  • Unexpected: 500 INTERNAL_ERROR with no stack trace or SQL
  • Body limit 100 KB

The web app

Pages: Landing, Discover, Trip, My Trips, Analytics, Login, Register, Profile, loaded lazily. A trip basket (context plus localStorage, max 10 stops) holds the chosen places; the route goes stale when stops, order or travel mode change. An algorithm comparison card shows ACO, nearest neighbour and brute force. Leaflet draws the map (OSM tiles, no key), Recharts the charts. Until Phase 2B, login, registration, profile and saved trips (max 50) live in browser localStorage and the password is only length-checked: demo mode. Sample data is labelled in the app.

Testing

Unit tests check one function alone (the gem rule, Dijkstra on a small hand-drawn graph with known answers, ACO against brute force on small cases). API tests (Supertest) call endpoints, including bad input. Tests need no database, internet or secrets: the database is a mock. The study guide states 277 backend tests (Jest) and 93 web tests (Vitest); this page copies that figure from docs/module-status.md and has not re-run them. ESLint and Prettier handle style. CI with GitHub Actions is planned for Phase 3.

1Why a backend at all? Why not call Supabase from the app?

To keep secrets off the device, keep all rules and algorithms in one place, and let web and mobile share one API.

2Walk through the four files of a backend module.

Routes: URLs and input rules. Controller: reads the request, sends the reply. Service: the logic. Model: the parameterised SQL.

3What does every API reply look like?

Success: {success:true, data}. Failure: {success:false, error:{code, message, details}}. Bad input gives 400, anything unexpected 500 with no internals shown.

4What is demo mode and when does it end?

Login, registration, profile and saved trips work on screen but live in the browser, and the password is only length-checked. It ends in Phase 2B, when Supabase Auth and the itinerary API are built.

5How do you test it without a database?

The database is replaced by a mock, so tests need no internet or secrets. Brute force checks ACO on small cases, and results are seeded so they repeat.

6List the security measures already in place.

Parameterised SQL, zod validation, hidden error details, RLS plus revoked public rights, helmet and CORS, no service_role key, secrets only in .env.

Google ratings (step 2.9a)

Match only if names are similar and positions within about 100 m, and report the match rate. Google’s terms only allow the place ID to be stored permanently, so ratings are refreshed by re-running the script. The reason not to scrape Google or TripAdvisor: it breaks their terms of service.
