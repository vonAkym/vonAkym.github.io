Terms to know

Software
Tells the computer what to do. Two types: system software and application software.
Web application
Software that uses the internet, follows W3C standards, is delivered through a browser and usually lives on a remote server.
Web Engineering
Extends Software Engineering to developing web apps (Software Development Life Cycle).
Murugesan et al., 1999
Uses scientific, engineering and management principles and systematic approaches to develop, deploy and maintain high-quality web systems.
Why it exists
Bring web development under control, minimise risks, and improve quality, maintainability and scalability.
Before Web Engineering
Informality (do your own thing), urgency (rapid decisions), intuition (feel your way), art (looks good).
Cutter, 2000
84% failed business objectives, 79% schedule delays, 63% budget overrun, 53% lacked functionality.
Front-end
Interaction design, creating UI design, interface programming.
Back-end
Logic programming, accessing the database, implementing security.
Web vs desktop: 8 traits
Network intensiveness, concurrency, performance, availability, content, aesthetics, security, data-driven.
First web page
Tim Berners-Lee, 6 August 1991.

Week 2

Requirements Engineering

Agree on the right thing before building it.

Problem

The wrong thing gets built: "That's not what I asked for."

→
Solution

Elicit and negotiate, document, validate and verify, manage change. Use Agile because change is constant.

→
New problem

Even right requirements can be derailed by people, technology and scope.

Mind map

Swipe sideways to see the whole map

The four activities, in order

  1. ElucidationElicit and negotiate. Stakeholders talk and reach consensus.
  2. DocumentationWrite the consensus in detail in a requirement document.
  3. Validation + VerificationRight thing? (validation) and done correctly? (verification)
  4. ManagementRequirements keep changing. Use methods and tools to absorb change.
Exam trap. Week 1 blamed informality, yet Agile lists informal methods. The difference: Agile informality is held in check by constant customer communication and small, early deliveries. It is not "do your own thing".

Terms to know

Requirement (IEEE 610.12)
(1) a condition or capability needed to solve a user's problem; (2) must be met to satisfy a formal agreement; (3) a documented representation of 1 and 2.
Stakeholder
A person or organisation with direct or indirect influence on the requirements: managers, customers, HR, government, owners, financial advisors.
Requirements Engineering
Eliciting, understanding, specifying and validating customers' and users' requirements (Escalona, 2004). Systematic and disciplined.
Elucidation
Elicitation and negotiation: a learning and consensus-building process through communication.
Documentation
Turn the agreed consensus into a detailed requirement document.
Validation
"Did we specify the right thing?"
Verification
"Did we specify things correctly?"
Requirements Management
Change is normal in web projects, so you need methods and tools to integrate new requirements and changes.
Agile Web Engineering
Customer satisfaction, early incremental delivery, small motivated teams, informal methods, minimal work products, simplicity. Delivery over analysis and design, plus continuous communication.
Why Agile
Business rules change fast, management wants instant results, and stakeholders keep changing their minds.

Boss fight

Tap a question to reveal the model answer. Try it in your head first.

1Why do we need both validation and verification?

They catch different mistakes. Validation checks you are building the right thing (matches real needs). Verification checks it is specified correctly (clear, consistent). A document can be perfectly written yet wanted by nobody, or wanted by everybody yet so vague it is misread. Either gap ends in "That's not what I asked for."

Verification = built the thing right. Validation = built the right thing.

2A neat, unambiguous requirement document describes a social feed, but students only wanted timetable and assignment reminders. Which question passed? Which failed? Which activity should have caught it? Name two stakeholders.
  • Passed: verification (clear and correct on paper).
  • Failed: validation (wrong thing).
  • Activity: Validation and Verification. Also Elucidation, since the real need was never properly elicited.
  • Stakeholders: students/customers (want reminders), owners or management (may want engagement), university or government (rules, privacy), managers (budget, schedule).

From risk to action

  1. PrioritiseUse the score. High and Critical first.
  2. Define responseAvoid, Mitigate, Transfer or Accept.
  3. Plan actionsSpecific steps, owner, target date, resources.
  4. ImplementFit into schedule, budget and resources.
  5. Monitor + reviewCheck it worked, update the score, act again.
Avoideliminate the risk
Mitigatereduce likelihood or impact
Transfershare the risk
Acceptmonitor the risk
Exam traps. Probability means how likely, not when. And Transfer (share it, e.g. a vendor or insurance) is not Accept (do nothing but watch).

Three types of risk

Operational or Management

Planning, coordination, people, resources, decisions.

Manpower shortage, poor team communication, delayed approvals

Hits timeline, budget, team productivity

Technical

Technology, dev tools, integration, system performance.

Bugs, tool or platform incompatibility, server failure, security holes

Hits quality, reliability, security

Project Scope

Requirements or deliverables unclear or constantly changing.

Changing user requirements, unclear objectives, extra features

Hits scope, schedule, cost, client expectations

Why classify? Shows the source of the risk, makes planning easier, improves monitoring.

Terms to know

Risk
Possibility of any negative occurrence from external or internal factors that can prevent the project goal. All projects have risks. Can be mitigated by preventive action.
Risk management
Minimise risks and prevent failure, keeping timeline, budget and application quality safe.
1 Risk identification
Find the likely or high-impact risks (e.g. manpower shortage, delay in modelling, extra storage).
2 Risk analysis
Judge severity by assigning an impact factor; the project manager prioritises.
3 Risk planning
Plan actions, starting with the highest-impact risk.
4 Monitoring and control
Run the project, keep assessing risks, foresee new ones.
Risk score
Probability x Impact. Example: key developer leaves, 4 x 5 = 20, Critical.
Avoid / Mitigate / Transfer / Accept
Eliminate / reduce / share / monitor.

1Why does the score multiply probability by impact instead of using impact alone?

Impact alone ranks a rare disaster (say, Malaysia going to war) above likely everyday problems and wastes planning effort. Probability asks how likely (not when), impact asks how bad. Together they show where effort pays off: a 1 x 5 risk scores 5 (Medium), far below a 5 x 3 risk at 15 (High).

2Score, level and type: A) client keeps adding features (P5, I3). B) server crashes at launch (P2, I5). C) manager slow to approve the design (P2, I2). Then pick a strategy for A.

Terms to know

Modelling
A conceptual illustration of the web app using diagrams, graphics, text and flowcharts to show content, function, architecture, components, interfaces, navigation and aesthetics.
Why model
Requirements and proposals are written in words, and words are ambiguous (the watering-can example).
Web Engineering process model
Communication, Planning, Modelling (Analysis + Design), Construction, Deployment, repeated per increment.
What to model (U-C-I-F-C)
Users, Content, Interaction, Functionality, Configuration.
Modelling interaction
The "conversation" between user and app. Tools: use cases, sequence diagrams, state diagrams, UI prototypes, navigation model.
Modelling content
Text, graphics, images, video and audio.
Prototype
Shows UI, content, interaction and aesthetic. Links are not active but show how it works, and it changes before the final interface. Users get what they want sooner.
Configuration
Server, hardware, OS, where the web server lives (cloud or intranet), server-database interoperability, client browsers (iOS, Windows, Android). Only a think-tank now; Week 6.

Boss fight

Tap a question to reveal the model answer. Try it in your head first.

1"We have a use case diagram, so a sequence diagram is a waste." Respond.

A use case diagram says what each user can do (actors and functions), with no order or timing. A sequence diagram shows how one process happens step by step over time, including branches like payment success or failure. A use case says "the customer can place an order"; only the sequence diagram shows what the system does to make it happen.

2Food-ordering app (customers, restaurant owners, admin). Which diagram for roles? Database design, and how does it map? Payment flow over time? Which thing to model waits until Week 6?
  • Roles: user diagram.
  • Database: class diagram. Classes become tables, attributes become columns, relationships become primary and foreign keys.
  • Payment flow: sequence diagram.
  • Week 6: Configuration.

7 design goals

  • SimplicityAll things in moderation. Avoid feature-bloat.
  • ConsistencySame look, templates and navigation behaviour everywhere.
  • IdentityAesthetic, interface and navigation suit the application domain.
  • RobustnessRelevant content and functions the user can rely on.
  • NavigabilityUsers can move around without hunting for links or instructions.
  • Visual AppealLook and feel, layout, colour, balance of text and media.
  • CompatibilityWorks across hardware, connections, operating systems and browsers.

5 quality attributes

  • Usabilitysite understandability, feedback and help, interface and aesthetics
  • Functionalitysearching, navigation, domain features
  • Reliabilitycorrect link processing, error recovery, input validation
  • Efficiencyresponse time, page and graphics speed
  • Maintainabilityease of correction, adaptability, extensibility

Interaction design: 3 questions, 13 principles

  1. Where am I?Show which part of the app and where in the content hierarchy.
  2. What can I do now?Show available functions, live links, relevant content.
  3. Where have I been, and where am I going?Give a "map" of past and possible paths.

The slide lists 13 distinct principles (Communication appears twice). The four groups below are a memory aid, not slide wording.

Guide the user

  • Anticipationanticipate the next move
  • Controlled Autonomyfree movement, but follow navigation conventions
  • Visible Navigationthe illusion of staying in one place
  • Track Statelog off and resume where you left

Talk to the user

  • Communicationshow the status of what they started
  • Readabilityreadable by young and old
  • Metaphorfamiliar analogy, if appropriate

Keep it easy

  • Consistencysame controls, icons, colours, layout
  • Learnabilitylittle to learn, little to relearn
  • Focusstay on the current task
  • Flexibilitydirect paths and free exploring

Save time

  • Efficiencyoptimise the USER's work, not the developer's
  • Latency Reductionmultitask so users need not wait
Exam trap. The Efficiency principle is about the user's efficiency, not the web engineer's or the client-server environment's.

Interface design workflow

Each step uses the result of the one before. Step 1 reuses Week 4's models, step 2 reuses the prototype idea.

  1. Review user characteristics, tasks and use cases from the analysis model; refine.
  2. Make a rough design prototype of the interface layout.
  3. Define the user tasks tied to each action.
  4. Make screen images for each interface action.
  5. Refine layout and screens using aesthetic design input.
  6. Identify the user interface objects needed.
  7. Write a procedural representation of the user's interaction.

1Interaction design must answer three questions. What goes wrong for the user if each is not answered?
  • Where am I? Users feel lost and can't tell which part of the app they are in.
  • What can I do now? They don't know which functions or links are available, so they stall or guess.
  • Where have I been / where am I going? They can't retrace steps or plan a path, so navigation feels random.
